# 1.1.0 Beta 7 — scan candidates, 5 GHz priority and DFS STA targets

Branch: `1.0.0-beta`. Numeric bundle version `1.1.0`.
DriverBuild: `1.1.0-beta.7-band-priority`. Stable `main` is unchanged.

## Install

The download is one ZIP with `AirPortRTW.kext/`, `rtw88-roam` and these notes
directly at its root. There is no ZIP inside it. Replace the kext in
`EFI/OC/Kexts/`, preserving `AirPortRTW.kext/Contents/Info.plist`, and reboot once.
RTL8821CE personalities have both roaming switches enabled, as in Beta 6.
Other cards remain opt-in. Keep the test tool outside the kext.

When downloading a GitHub Actions artifact directly, file execute permissions
may not be retained. From the extracted directory, run if necessary:

```sh
chmod +x ./rtw88-roam
```

## Discover actual BSSIDs first

```sh
sudo ./rtw88-roam --log-level verbose
sudo ./rtw88-roam --discover
./rtw88-roam --aps
```

Discovery does not request a disconnect or an AP switch. It visits at most
64 enabled channels in the device's 2.4/5 GHz table, returning to the current
AP channel between slots. It can briefly interrupt data traffic. The worker
has a 25-second software deadline; the tool waits at most 30 seconds. These
deadlines cannot interrupt a stuck hardware/MMIO operation.
Normal CoreWiFi background scans remain cache-only.

`--aps` lists only cache entries with the connected network's SSID, including
their real BSSID, channel, frequency, signal, observation/beacon age and the
eligibility reason. It lists stale entries too, explicitly marked by reason;
it is not itself an RF scan. At most 64 entries are printed. A router's device
or LAN MAC is not assumed to equal its WLAN BSSID.

## Test an explicit target

Use a BSSID actually listed by discovery, not an inferred device MAC:

```sh
sudo ./rtw88-roam --prepare aa:bb:cc:dd:ee:ff
sudo ./rtw88-roam --roam aa:bb:cc:dd:ee:ff
```

`--prepare` now performs discovery + check. It does not request an AP switch.
`--roam` performs discovery + the existing controlled switch to that explicit
target; it does not substitute a different AP according to band preference.
A successfully completed discovery may be reused for five seconds after
completion. Every final eligibility check still enforces observation freshness.
The Neighbor Report is no longer required for these commands.

`--scan BSSID` retains a single-channel diagnostic scan if that target's channel
is already known from the scan cache or a fresh Neighbor Report. An unknown
target without a channel hint needs `--discover` first. A fresh Neighbor Report
alone cannot authorize the actual AP switch.

## Prefer 5 GHz with a 2.4 GHz fallback

```sh
sudo ./rtw88-roam --best
sudo ./rtw88-roam --roam-best
```

`--best` recommends from existing fresh scan entries without scanning or
switching. `--roam-best` discovers first, selects and switches only if the result
is a different eligible AP. Neither command enables continuous automatic
roaming. There is no new background scanner, timer or roaming daemon.

Initial beta policy, also published in diagnostics:

- New 5 GHz candidates at **-70 dBm or stronger** receive priority over 2.4 GHz.
- An existing 5 GHz connection is retained down to **-77 dBm**, unless another
  suitable 5 GHz candidate is sufficiently better. This separates enter/leave
  thresholds to limit band ping-pong.
- Below that threshold, an eligible 2.4 GHz candidate outranks weak 5 GHz.
  If 2.4 GHz is unavailable, usable weaker 5 GHz can still be retained/selected.
- Candidates below **-80 dBm**, or with invalid RSSI, are rejected.
- Same-band changes require at least **6 dB** improvement over a valid current
  signal. The current AP participates in the choice and can be the best result.
- The existing **60-second switch cooldown** and **one fallback attempt** remain.

This uses signal and eligibility, not measured throughput, load or airtime.
The thresholds are initial test values, not proof of an optimal RF decision.

## DFS and passive-only channels

DISABLED channels remain rejected. RADAR/no-IR flags are preserved; they are
not cleared to enable active probing. Discovery and targeted scans send no
probe requests on those channels and listen for 180 ms per slot.

A STA roaming target on a RADAR/no-IR channel additionally requires a fresh,
complete ESS AP beacon with matching transmitter/BSSID, no fragmentation,
and matching advertised channel/RX frequency. A probe response or Neighbor
Report alone is insufficient. Beacon age is not refreshed by probe responses;
it is preserved only across coherent same-BSS observations.

The ordinary managed-client connection/handshake path is then used. This is
experimental STA operation under an existing AP, not AP-mode radar detection,
CAC implementation or a claim of complete DFS/CSA support. It must be tested
on hardware. The existing normal connection path already supports DFS APs;
this change removes the extra blanket roaming rejection with an RF-proof gate.

## Logs and test outcome

```sh
sudo ./rtw88-roam --watch 45 > ~/Desktop/AirPortRTW-Beta7-Watch.txt
sudo ./rtw88-roam --report > ~/Desktop/AirPortRTW-Beta7-Report.txt
```

Beta 6's event IDs/timestamps, handshake stages, AP status/deauth reasons,
power cancellation and runtime log levels remain. Additional fields include
`target_source`, `recommended_bssid`, band thresholds, scan completion age and
the `ap[]` records. A rejected new single-target scan resets its old scan result,
so an earlier successful scan is not presented as this attempt's success.

Switch result meanings remain: 0 none, 1 target pending, 2 fallback pending,
3 target locally keyed, 4 fallback locally keyed, 5 both failed, 6 canceled.
Local key state/M4 submission is not AP acceptance or IP reachability. Check
the resulting BSSID, gateway access and real traffic after a successful switch.
An unchanged current BSSID with `current-ap-preferred` is a deliberate no-op.

Host tests execute production discovery, filtering and selection using OS/RF
mocks: missing Neighbor Reports, fresh/stale scan entries, disabled channels,
passive DFS/no-IR probe suppression, beacon validation, band preference,
2.4 GHz fallback, same-band hysteresis, PM fencing, cancellation, snapshots,
key handling and the one-shot fallback. Native CI builds the x86_64 kext/tool
and enforces compiled IOCTL stack budgets. This is not over-air roam/DFS or
sleep validation. No FT, PMF or WPA3 implementation is added.
