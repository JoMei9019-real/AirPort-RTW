# AirPortRTW 1.1.0 Beta 11 — Beacon Reports

Build: `1.1.0-beta.11-beacon-reports`; numeric bundle versions remain `1.1.0`.
Install the kext in the same OpenCore entry as Beta 10, replace the helper with
the one in this package, then reboot. One ZIP contains the raw kext, helper and
these notes. No stable-main changes or nested archives.

## Implemented scope

- Existing 802.11k Neighbor Report request/response support remains enabled.
- Association RM Enabled Capabilities advertises Beacon Passive, Active and
  Table, conditionally on the supported WPA2/CCMP mode and available scanner/
  control timer. Neighbor Report is advertised separately when the AP supports it.
- Radio Measurement requests from the current AP: up to eight measurement
  elements, bounded parsing, dialog/measurement token preservation, and explicit
  incapable/refused reports for unsupported options or an unavailable radio.
- Beacon Table uses a separate bounded 32-record cache of exact received frame
  bodies (up to 768 bytes), at most 30 seconds old. Reports may include other
  SSIDs if the AP requests a wildcard. Results are capped at 16 BSSs per request;
  an oversized result set is refused rather than silently called complete.
- Passive measurements perform a fresh listen without Probe Requests. Active
  measurements send wildcard/directed SSID probes only on legal active channels.
  DFS/no-IR channels remain passive-only; disabled channels remain excluded.
- Global 20 MHz operating classes 81, 82, 115, 118, 121, 124 and 125; individual
  channel, all channels in one class, or channel 255 with same-class AP Channel
  Report subelements. Up to 16 channels and 200 ms dwell per channel, home-channel
  return slots, existing cancellation and a 15-second transaction deadline.
- Only observations from the new scan generation and actual measurement slot
  qualify as fresh measurements. Passive reports require received beacons.
- Beacon body reporting supports detail 0/1/2, SSID/BSSID filtering, requested
  IE selection, frame-body fragmentation and Last Beacon Report indication.
- RCPI comes from measured RSSI; unavailable RSNI is 255 and antenna ID is 0.
  Table TSF/duration fields are zero. Physical start TSF uses a fresh requesting
  AP beacon plus host elapsed microseconds, explicitly logged as a software
  anchor; its over-air timing accuracy is not hardware-validated. Parent TSF
  uses the receive descriptor's low TSF. Mandatory-duration requests are rejected.
- Existing controlled 802.11v BTM, automatic band preference and full WPA2
  reconnect/fallback are retained. No FT/802.11r, SAE or PMF is added.

## Not claimed

This build does not implement every optional 802.11k/v service: Link Measurement,
channel-load/noise-histogram/statistics/location reports, parallel/repeated or
triggered measurement operation, wide-band/country-specific operating classes,
extended requested-IE lists and conditional Beacon Reporting remain unsupported
and unadvertised. Unsupported measurement elements receive incapable responses.
An indivisible IE that cannot fit the bounded report element is rejected; large
frames over the capture limit are not included as successful observations.

WPA2/CCMP with the internal PSK supplicant is the supported test path. Enterprise,
PMF-required associations and external-supplicant operation do not advertise the
new capabilities. `-rtwnoautoroam` disables automatic/BTM-triggered AP changes;
Beacon Measurements remain available independently of that automatic policy.

FRITZ recognition, AP-triggered measurements, response ACKs and actual BTM
switching require hardware testing. The existing successful manual switches
were on the same channel; cross-channel roaming remains unvalidated. Earlier
unexplained boot panic and deep-sleep reliability are not declared fixed.

## Diagnostics and test

Run from the extracted directory containing `rtw88-roam`:

```sh
ioreg -r -c AirPortRTW -l | grep -E 'DriverBuild|ROAM_K_ADVERTISED|ROAM_K_BEACON|ROAM_V_ADVERTISED|ROAM_V_MODE|ROAM_AUTO_ENABLED'
sudo ./rtw88-roam --log-level verbose
sudo ./rtw88-roam --watch 300 > ~/Desktop/AirPortRTW-Beta11-Watch.txt
sudo ./rtw88-roam --report > ~/Desktop/AirPortRTW-Beta11-After.txt
```

Check the connected device's FRITZ signal properties for 11k/11v. Move toward the
other AP during capture and stay there for at least two minutes. Avoid manual
`--roam` commands during the automatic test. Router capability recognition alone
does not prove it sent a Beacon Measurement or BTM request.

Snapshots include `rm_*` counters/stage, last dialog/token/mode/channel/status,
request parse offset, measurement scan generation, submitted reports, TX ACK/
no-ACK, incapable/refused/empty results and cancellation. `btm_*` now includes
request/invalid/accept/reject/switch counters. Readiness-drop counters distinguish
BTM and measurement requests that reached the driver while scan/AWDL/PM gates
prevented processing. Logs show request flags, operating class, requested dwell,
scan mode, reported BSSID/RSSI/result age, fragment count and TSF source.
Submission counters are not delivery/connection proof; ACK counters are separate.

Outstanding Neighbor Reports now defer automatic discovery, preventing the known
request-immediately-before-scan race. Measurement transactions arbitrate with
BTM, automatic discovery, manual commands and AWDL; busy operations are refused
or canceled. Requests that arrive while the existing RX readiness gate is closed
are counted/logged, not secretly treated as processed. This limitation remains.

Beacon bodies can contain SSIDs/BSSIDs. Diagnostic output does not log WPA keys,
EAPOL payloads, passwords or user IP data.

## Validation and next milestones

Production C++ parser, scanner and transaction methods are executed under host
ASan/UBSan, including malformed/fuzzed input, report fragmentation, passive probe
suppression, active-channel rules, DFS, fresh-generation isolation, busy/PM/
clock/TX failure cases. Existing k/v, roaming, PM/RX/workqueue and compiled native
stack-budget checks remain required in macOS CI.

Beta 12 should address real AP request/reply traces and any format/operating-class
gaps they reveal. Beta 13 is the target for validating the roaming-related k/v
path, including actual BTM requests and cross-channel tests, not a promise of all
optional services in either standard. Hardware results determine readiness.
